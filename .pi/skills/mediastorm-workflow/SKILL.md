# MediaStorm 开发工作法

用户只需描述目标，不需要学习 /storm 或其他内部命令。普通咨询直接回答；明确的开发、修复或优化请求由你调用 storm_task(action=new, title=目标摘要) 建立记录。补充需求沿用当前任务。用户说“继续上次的工作”时调用 storm_task(action=resume)，恢复后先说明已确认内容与下一步。不要用关键词匹配猜业务意图。

接手、调查、优化已有项目时选择 agent=project-takeover，并读取 project-takeover 技能；明确的功能开发或修复可选择 agent=development。新任务默认 project-takeover，旧任务未记录 Agent 时保持通用开发流程。用户可以自然语言要求查看或选择助手，工具 action=agents 返回配置；切换任务恢复其原助手，不覆盖已确认方法。

先读取当前任务的 prd.md、可选 design.md、implement.md、progress.json，以及相关项目规范。文件中的当前记录优先于旧对话。项目级经验放在 .trellis/spec；本次需求和决定放在当前任务，避免复制其他项目的结论。

每个新任务用 storm_task(action=memory, query=相关主题) 查阅本项目已验收交付及经验；没有相关主题时可省略 query。记录关联任务、验收时间和原文件来源，先核对当前文件再使用。原始记录保留在任务中，工具也可读已归档任务；不得把未验收推测当作已确认记忆。成熟的工程约定仍按项目既有方式维护在 .trellis/spec，工具不会自动覆盖规范。

## 回顾上次工作

“上次优化了什么”“还有什么没处理”属于只读咨询，先用 storm_task(action=memory)，不新建任务，也不为查看已验收记录调用 resume。只有具体主题才传 query；筛选没有结果时先取消筛选核对，不能据此说项目没有记录。

默认上下文只给有限摘要。按工具返回的 task 读取该目录 progress.json：handoff 是已验收交付和遗留事项，check 是实际检查命令、时间、退出状态和输出，assessment 是当时的调查。需要确认设计理由再读 prd.md/design.md。记录确实缺失或无法读取时说明具体文件和原因；未读取不能称“只能看到 PRD”或“没有记录”。

回答依次说明实际完成、历史检查结果、未解决事项和适用的设计决定。检查数量、跳过原因以 check.stdout/stderr 核对；区分过去通过与本次重跑、退出成功与全部覆盖。遗留以交付 remaining 为起点，原调查用于补充原因；较新记录或代码可能已解决旧问题，应核实后再建议继续。“不需要抽象”“保持原行为”等已确认取舍不自动变成待办，PRD 的范围排除项也不全部等于问题。纯回顾不重新运行检查、不改变验收状态。

## 用户只说“优化一下项目”时

先只读调查入口、有效规则、相关实现和已有检查，给出最多三个有文件依据的问题及其影响，推荐先处理哪一个。不要把历史说明当现状，也不要把“优化”解释成全仓库重构。只问当前最影响范围的一个问题，例如优先解决启动困难、维护困难还是某个慢操作；能从代码查明的事实自己查。

和用户确定一个本轮目标后，明确预期变化、必须保留的行为与验收办法。未运行的检查只说待验证；基线检查安排在获准的执行阶段，修改前先跑。需求、方案和检查方式准备好后再请求一次实施确认。

每项验收条件都要写明验证方法：哪条命令、哪个可检查的产物，或对照哪些源码做静态核对。方法必须能发现该条件未达成，不能用“字段名出现了”代替含义、默认值、启用条件或依赖关系的核对。

## 澄清需求

1. 先调查代码。结构问题使用 CodeGraph，已知文件和字面文本使用 read/grep。索引缺失时说明并询问是否初始化，不能假装查过。
2. 逐题提问，一次只问一个问题，附推荐答案及其影响。能从现有代码确定的事实自行查看。不要重复问已确认项。
3. 每次用户回答后更新 prd.md：目的、已确认需求、未确定事项、范围、验收条件。复杂任务补 design.md、implement.md；简单任务在 prd.md 说明做法即可。
4. 调用 storm_progress，把 phase 设为 clarify，并记录当前问题和下一步。不要在这一步修改业务代码或执行命令。
5. 需求收敛后明确真实检查命令，调用 storm_progress：phase=awaiting_approval，checkCommand=该命令。用通俗语言展示需求、方案和验收方式，再调用 storm_task(action=approve) 打开确认界面。只有实际返回 applied=true 且阶段为 implementing 才开始实现。取消后等待新意见，不反复弹窗，也不要求用户输入命令。

## 实现和检查

用户确认后，自动按已确认方案实现，遵循 Ponytail 和本项目规范。每个有意义的阶段用 storm_progress 记录当前改动与下一步，不给虚假百分比，不为每次读文件或改代码索要许可。

如果需要改变已确认的需求、方案或检查命令，回到澄清并重新确认。确认不包含自动发布、推送代码、向别人发消息或修改生产环境。

实现后调用 storm_check。它会执行已确认的命令并保存实际输出；失败就修复并重试。不得用自己写的“通过”代替检查，不得编辑 progress.json 或用其他工具调用这个工具来绕过确认。发生工具失败、中断或模型空闲都不能视为完成。

## 交付和继续

交付前重读已确认的验收条件，逐项核对当前差异和产物。用简短列表或表记录“要求 → 证据/方法 → 实际结果与未覆盖范围”；小改动几句话即可，不增加重复报告文件。区分程序执行、源码静态核对和仍待使用者验证的内容；静态检查通过不能称服务可运行或业务效果已验证。

配置/说明类改动，核对合法值、默认值、何时需要、依赖与用途，并确认配置赋值和原业务行为是否改变。只扫配置名最多证明名称覆盖，源码核对还应查到实际读取处及相关调用路径。验收条件在已确认范围内有缺漏时先修复；必要条件仍未验证时如实说明，不宣称全部完成，也不悄悄降低标准。扩大范围或改变已确认检查命令仍按原确认流程处理。

检查通过后，说明代码改了什么、如何运行、实际检查结果、仍需人工判断的部分；需要时更新简短项目经验。最后调用 storm_progress：phase=awaiting_acceptance，再用 storm_task(action=accept) 请求用户验收。实际返回 completed 才算验收完成。

可用 storm_handoff 保存交付摘要、运行说明、遗留事项和附带文件来源的经验；它们会随实际用户验收一起确认，并供后续任务检索。项目接手助手必须先保存调查及交付报告，通用开发任务可以按需使用。报告不能代替真实检查；业务修改或重跑检查后重新整理交付。

逐项核对的证据和结论可写入交付 summary/runInstructions；未覆盖内容及原因写 remaining，已确认的设计取舍写 summary 或 memories，不自动列为待解决问题。工具保存真实命令结果，但不自动判断所有验收条件的语义，不能把工具接受报告当作质量证明。

恢复任务时先展示读取了哪些项目文件、已经确认什么、目前在哪一步，接着推进下一步。需求和任务记录来自项目；多个未完成任务由工具展示选择，不擅自猜测。原始对话可使用 Pi 自身会话恢复。/storm 系列命令只是备用入口，不是使用者必学的步骤。
