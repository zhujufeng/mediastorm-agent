终端试用已经完成两个连续任务及一次较完整的历史恢复；用户指出仍不能直接交给同事使用。下一阶段转为桌面交付：首次使用、模型接入、打开项目、真实对话/确认/执行/交付、重启恢复，以及目标系统的安装包。完成标准是另一位同事在自己的电脑独立走完流程，详见 [桌面版交付范围](desktop-pilot.md)。操作系统和模型接入方式已向用户询问，技术框架由开发实现需要决定。

## 最新确认的产品与首个交付（2026-09-09）

产品定位已收敛为基于 Pi 的公司 Agent 平台，桌面应用为主要入口。规划、任务恢复、项目记忆、进度和关键确认共用；按同事需要交付的任务定义专用 Agent。

首个 Agent 是“项目接手与优化助手”：调查已有 AI 开发项目，确认一个改进范围，实施和检查后交付运行说明、遗留事项和有来源的项目经验。原通用开发流程作为另一配置保留，两者复用同一套机制。

当前已经实现终端原型中的助手选择、调查/交付门槛、验收后经验读取和旧任务兼容，并通过离线回归。2026-09-10，使用者已在预测项目完成并验收一次静态测试改进（2 passed / 1 skipped），记录了项目经验。试用暴露了重开时选错项目的问题；入口已增加项目选择、最近记录、持续路径显示及本机 Mac 双击脚本。下一步核对重开业务项目后的模型记忆恢复、更多任务判断质量，再推进桌面界面和安装分发。正式桌面版的初始操作系统及 UI 框架尚未选定。

以下分阶段原则继续适用；候选任务以本节确定的首个 Agent 和预测项目试用为先。

## 想得到的实际效果

一个同事提出小型开发需求，助手带他确认需求、复用公司已有做法、改代码、运行检查；另一位开发者能看懂产物并接手修改。

比如“给现有报表增加一个筛选条件”或“给现有采集程序增加一种同类数据”。这些是候选例子，尚未选定真实试点。

## 先完成一个任务，再扩大范围

### 第一步：选项目，整理可参考的做法

选一个现成项目、一个边界清楚的小需求，以及能判断对错的样例。

记录程序入口、运行方法、配置来源、错误处理和检查命令。梳理已有项目可以帮助找出共同做法；不能把未经源码和运行结果验证的建议当公司标准。

**完成标志**：另一位开发者按照说明可以运行样例，并知道怎样判断结果正确。

### 第二步：让 Pi 完成一次受控开发

2026-09-09 已确认：第一轮先由开发者使用 Pi CLI，验证开发流程；桌面应用作为正式员工入口。

在选定项目的独立工作副本中，通过 Pi 终端入口加载相关规范和工具：

1. 读取需求和相关范例。
2. 提出需要确认的业务问题，保存确认后的需求。
3. 编写一个小改动。
4. 运行该项目真实的检查命令。
5. 输出代码差异、检查结果、运行说明和仍需人工判断的问题。

此时先用开发者入口验证。项目路径应明确指定；模型服务选用公司允许的配置。执行程序负责保存真实结果，模型负责解释。

**完成标志**：正常需求能完成，检查失败能如实报告；另一位开发者可以接手修改。失败后仍能找到已经产生的代码和检查记录。

### 第三步：给业务同事一个简单入口

用户能看到并操作：

- 选择允许使用的项目或能力，描述需求。
- 确认业务要求，查看样例。
- 查看正在做什么，必要时停止。
- 试用产物，查看改动与检查结果。
- 把交付交给负责人审查。

公司允许安装内部桌面应用。第一版通过公司分发渠道提供安装包，在应用中完成项目选择、需求澄清、方案确认、执行检查和交付；关键节点确认，中间步骤自动推进，并持续显示当前阶段。

实现建议是由应用管理本机 Pi、工具与必要运行环境，复用试点验证过的技能和项目记录。需要适配桌面界面的终端组件另行实现。首批操作系统、UI 框架和模型接入方式尚未确定，具体交付边界见[工作流与产品交付](pi-workflow-proposal.md)。

**完成标志**：另一位同事在自己的电脑上完成安装、打开项目、完成一个小任务，退出后能恢复任务；升级后代码和项目记忆仍可继续使用。记录人工帮助次数和卡住的原因。

### 第四步：把一个成功案例变成可复用能力

把适用条件、程序、参数、样例和检查方式一起保留。让第二位同事完成相似任务，再判断哪些部分值得统一。

数据采集能力可逐步增加 HTTP、浏览器插件和 RPA，优先复用已有工具。不要为了凑齐三种技术，同时开发三套引擎。

**完成标志**：第二次交付更省事，结果依然通过同样的检查；换人维护不依赖口头补充隐藏步骤。

## 第一版先不承担的工作

完整 IDE、通用插件市场、全公司资产平台、任意网站采集和自动生产发布，均不属于首个试点。

这些能力是否需要，应由真实使用中的问题决定。
