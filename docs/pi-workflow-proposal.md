# Pi 开发工作流定制草案

## 已确认：公司 Agent 平台与首个助手（2026-09-09）

用户已确认并授权开发：以 Pi 为底座提供面向不同任务的 Agent，桌面入口支持选择助手或直接描述需求。公共机制包括规划、任务恢复、项目记忆、进度展示和关键节点确认。各 Agent 定义职责、工作方法、工具需求、操作范围和交付标准；插件可以复用，不要求每位助手都使用不同插件。

首个助手帮助同事接手和改进用 AI 开发的项目。当前已在 Pi 原型实现专用调查、确认前的文件依据、检查后的交付报告和验收后的经验检索。原通用开发配置保留，旧任务继续使用原方法；两个配置本轮共用固定扩展集合。

项目记忆以当前项目已验收任务为来源，包括交付摘要、运行说明、遗留事项和附带文件来源的经验。任务记录保留验收时间与检查证据，归档后仍可查询；取消不形成已确认记忆，内容变动必须与验收指纹一致。成熟规范另行维护在 .trellis/spec，不重复建立自动同步的记忆库。对话上下文压缩复用 Pi，本轮未增加向量数据库、插件市场或桌面框架。

离线回归验证了工具与状态约束；真实模型完成一次业务任务、同事的安装使用和桌面交付仍待验证。下文早期调研内容作为来源保留，当前操作以 docs/pi-pilot.md 为准。

## 自然语言作为主要入口（2026-09-09 用户进一步明确）

最终体验参照 Codex：选择项目后直接说“帮我优化当前项目”，助手承担调查、任务记录、需求澄清、方案整理、实现、检查及交付。使用者不需要知道 Trellis、CodeGraph、Ponytail 或工作流命令怎样配合。

宽泛请求先调查，再展示少量有依据的问题并推荐本轮重点；一次只问一个关键问题。方案要同时说明预期变化、保持不变的行为和验证方式。使用者确认后自动实现与检查，交付时再验收。界面持续显示正在调查、等待回答、等待确认、实施、检查或待验收。

正式桌面入口只需项目选择、自然语言对话、阶段提示、方案确认和交付差异。需求文件、检查命令、任务目录和插件装载由系统处理；开发者需要时可展开查看。说“继续上次的工作”即可恢复项目任务，有多个候选时展示选择。

当前终端原型已增加模型可调用的任务控制工具，命令降为备用入口；普通咨询不要求建任务。关键确认仍由实际 UI 返回决定，模型不能自行批准。底层工具链已通过离线回归；自然语言理解质量、桌面界面及完整业务交付尚待验证。

2026-09-09。本文保留需求和插件调研依据。后续已实现 `/storm` 本地原型并通过离线回归；当前状态与操作见[原型使用说明](pi-pilot.md)。桌面应用和真实模型业务试点仍未完成。

目标是在 Pi 内完成逐步澄清需求、按规范开发、检查交付，并让使用者随时知道当前在做什么。加入 Ponytail 约束不必要的复杂度，加入 CodeGraph 定位代码，保留项目级记忆。开发同事与业务同事都要覆盖，第一轮先验证 Pi 终端体验。

## 当前建议

复用现有 Trellis 作为需求、任务与项目知识的记录方式，接入 Ponytail 和经过兼容检查的 CodeGraph 扩展；新增内容集中在中文阶段提示、明确的继续入口与跨会话恢复体验。

这里的需求 spec 对应每个任务的 `prd.md`，复杂任务再有 `design.md` 和 `implement.md`；`.trellis/spec/` 保存可复用的项目工程约定。前者说明这次要做什么，后者说明这个项目通常怎样做。

| 用户需要 | 已有基础 | 第一轮需要补齐或验证 |
| --- | --- | --- |
| 像 grill-me 一样逐步完善需求 | Trellis Brainstorm 已要求逐题提问、给建议、先查项目证据、每次回答后更新 PRD | 中文对话是否自然；已回答的问题不重复问；问题收敛到可检查的需求 |
| 每一步知道在做什么 | Trellis 有工作流阶段与任务状态；Pi 有状态栏及 widget API | 展示任务、当前阶段、已确认内容、等待事项和下一步；状态来自实际任务记录 |
| 代码保持简单 | Ponytail 4.9.0 有现成 Pi 扩展与技能 | 与项目检查及需求流程协调；精简代码时仍保留必要验证和解释 |
| 快速定位代码 | 本机 CodeGraph 0.9.4；有 Pi 社区适配包 | 固定适配包版本；显式绑定项目；索引缺失时说明原因；验证工具使用质量 |
| 项目级记忆 | Trellis 的 spec、tasks、workspace 文件，以及上下文加载机制 | 新会话能找到已确认决定、当前任务和下一步；多个任务时明确选择；避免跨项目带入 |

Trellis 依据：[官方工作流](https://docs.trytrellis.app/start/everyday-use)，本地 `.pi/skills/trellis-brainstorm/SKILL.md`、`.pi/prompts/trellis-continue.md` 与 `.pi/extensions/trellis/index.ts`。

## 希望用户看到的过程

建议流程：澄清需求 → 确认方案与验收方式 → 实现 → 实际检查 → 交付与记录。

需求澄清时，一个问题包含推荐答案及影响，回答后更新需求。能从代码和文档确定的事实由 Agent 自行查看。用户随时可以查看当前需求全文。

阶段展示目标示意（当前原型已提供阶段、工作、工具活动与下一步展示）：

```text
任务：给报表增加账号筛选
当前：澄清需求
已确认：筛选范围、输出格式
等待你决定：历史数据是否也需要支持
接下来：确认方案和检查方法
```

不展示无法客观计算的完成百分比。实现阶段应显示当前改动目标；检查阶段显示实际通过、失败和未执行的项目。回答停止、工具返回成功、代码变少，都不能独自代表交付通过。

本地 Trellis 会在 `before_agent_start` 注入任务变化，但运行状态消息使用 `display: false`；当前也没有主流程的 `setStatus`/`setWidget` 注册。因此“Agent 收到工作流状态”和“用户能看见当前步骤”之间存在需要补齐的体验缺口。子 Agent 的进度卡已存在，可复用其已有能力。

## 项目记忆应记住什么

| 内容 | 现有位置 | 写入与读取原则 |
| --- | --- | --- |
| 项目的工程约定、反复遇到的问题及防范方法 | `.trellis/spec/` | 把经确认或验证的经验归纳进去，记录适用条件；开始相关开发时读取 |
| 需求、方案理由、验收方式与待办 | `.trellis/tasks/<task>/` | 澄清和阶段切换时更新；继续任务时优先读取当前文件 |
| 历次工作摘要、相关改动和未解决问题 | `.trellis/workspace/` | 留下简短记录及来源，让下一会话能定位相关任务 |

项目文件可随仓库交接和审阅；需要记录的是可以帮助后续决策的事实。原始聊天保存在会话中，长期规范只收录提炼后的内容。新会话应显示“已恢复哪些项目记录”；记忆冲突时以当前代码、检查结果和最新确认决定为准。

项目知识应按当前仓库定位，不能仅以文件夹名称定位。存在多个未完成任务时应让用户选任务，不直接猜测。是否共享哪些工作日志，需要与团队实际协作方式一起确认。

CodeGraph 保存代码结构，Trellis 文件保存需求和决策理由，两者分别解决不同的检索问题。[CodeGraph 官方说明](https://github.com/colbymchenry/codegraph)。

## 第一轮验收建议

1. 连续两轮中文问答后，需求记录包含已确认项、未确认项和验收方式。
2. Pi 能显示真实阶段、当前工作及等待事项；中断后不显示虚假的完成状态。
3. 确认后的一个小需求通过 Ponytail 约束完成修改，并运行项目检查。
4. CodeGraph 在正确项目查询；不存在索引或符号时有清楚反馈。
5. 退出并新开会话后能恢复任务和下一步；另一个项目不能读入该项目的需求与决定。

用户已确认：关键节点确认，中间步骤自动推进。需求和方案确定后自动推进实现与检查，交付时验收；每个小步骤保持可见，但不反复要求确认。这确定了流程偏好，完整实现范围仍以进一步收敛的需求为准。

## 已确认的产品交付形态

2026-09-09 用户已确认：公司允许同事安装内部桌面应用，桌面应用作为主要入口。Pi CLI 用于开发者验证工作流；下述执行、存储和分发方式为实现建议，首批操作系统与 UI 框架尚未确定。

正式员工入口为公司统一分发的桌面应用。用户打开应用、选择已有项目或新建项目、描述需求，随后在一个界面内回答问题、查看需求与方案、观察执行和检查、试用及交付产物。开发者可以查看代码差异和日志，业务同事优先看到需求与结果。

### 执行与存储

- Pi、工具和代码执行位于同事自己的电脑；模型请求走公司批准的服务。需要服务器项目时再增加远端执行方式。
- 应用管理经过验证的 Pi、Ponytail、CodeGraph 和必要运行环境版本；项目自身的构建、测试或浏览器依赖仍要通过项目模板及环境检查准备。
- 代码、需求、项目规范和任务记录位于对应项目；经审阅的共享内容随项目 Git 仓库交接。原始会话和本地缓存另行管理，CodeGraph 索引在每台机器重新建立。
- 能力包与项目产物分开更新。升级应用或扩展时保留项目自己的需求、代码和记忆，运行中的任务不因后台升级突然更换版本。

### 分发与更新

开发者试点可以使用一个固定版本的内部 Pi Package，把需要的技能、扩展和提示统一分发，配套启动与环境检查。正式桌面应用通过公司现有软件下载或设备管理渠道提供安装包，按实际同事的操作系统提供经过验证的版本。

Pi Package 支持 Git/npm 来源和版本固定；它解决资源分发，桌面安装、首次使用、更新与回退体验仍由本项目实现。[Pi Packages](https://pi.dev/docs/latest/packages)。

桌面应用可以通过 Pi 的 Node SDK 复用会话与扩展资源，必要时也可通过 stdio RPC 接入。需求方法、工具和项目文件继续复用；终端状态栏及自定义 TUI 组件需要适配新界面，不能假设装上 Pi Package 就得到图形应用。[SDK](https://pi.dev/docs/latest/sdk)、[RPC](https://pi.dev/docs/latest/rpc)。

### 各入口的定位

| 形态 | 适合情况 | 需要承担的工作 |
| --- | --- | --- |
| 定制 Pi 终端包 | 开发同事试点、已经熟悉终端 | 安装运行环境、统一配置、支持排错 |
| 桌面应用（已确认的主要入口） | 开发同事与业务同事的日常使用 | 安装分发、运行环境管理、图形界面与更新 |
| 公司内网页（暂不纳入第一版） | 以后出现集中执行、免安装的明确需求时评估 | 每任务执行隔离、服务器资源、身份与项目访问；使用本机资源时另需本地连接组件 |

网页登录不会自动获得同事电脑的项目、浏览器登录态或桌面操作能力。Pi 按所在进程权限执行；集中部署的隔离需要另行实现。[Pi 执行边界](https://pi.dev/docs/latest/security)。

桌面交付验收必须包含“在另一位同事的机器上，从安装到完成一个小任务，再退出应用并恢复任务”，并检查新版本更新后原项目和记忆仍可继续。当前的本机加载检查尚不满足这一标准。
